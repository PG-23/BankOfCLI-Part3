# API Contract: Bank of Airlines (Frontend ↔ Backend)

**Status:** draft v2.
**Source of truth for the TypeScript types:** `src/app/core/models/`.
**Mock data:** `src/app/core/mock/` and `public/mock/`. Mocks must follow this document exactly. If a model changes, update this file and the mock JSON in the same pull request.

---

## 1. Conventions

| Topic | Rule |
|---|---|
| IDs | Always strings (`"ML1001"`, `"AC1001"`, `"t7"`). |
| Money | JSON numbers in **USD dollars**, at most **2 decimals** (`1300.5`). Amounts in requests and records are always **positive**. `Transaction.type` decides the direction. |
| Dates | ISO 8601, UTC: `2026-10-07T14:30:00Z`. |
| Envelope | Every call returns `ApiResponse<T>` (section 2). |
| User ID | Generated by the **server**: first initial of first name + first initial of last name (uppercase) + a 4-digit number starting at `1001` that goes up by 1 for each new user. The counter is global, not per initials. Molly Lee → `ML1001`, then James Smith → `JS1002`. Clients never send an ID when registering. |
| Login | Users log in with their **user ID or email** plus password. There is no username. |
| Account number | String of exactly 10 digits (`"1000001001"`). |
| Accounts per user | A user can own several accounts (`CHECKING` and `SAVINGS`). The transactions page works with the user's `CHECKING` account. The dashboard shows all of the user's accounts. |
| Transfers | One transfer creates **two** transaction records: `TRANSFER_OUT` on the sender and `TRANSFER_IN` on the recipient, with the same timestamp. The call returns the sender's record. |

## 2. Response envelope

```ts
interface ApiResponse<T> {
  success: boolean;
  data?: T;          // present when success is true
  error?: ApiError;  // present when success is false
}

interface ApiError {
  code: ApiErrorCode;
  message: string;   // safe to show to the user; never a stack trace
}
```

Success:

```json
{ "success": true, "data": { "id": "t7", "accountId": "AC1001", "type": "DEPOSIT", "amount": 50, "balanceAfter": 2500, "createdAt": "2026-10-07T20:15:00Z" } }
```

Error:

```json
{ "success": false, "error": { "code": "INSUFFICIENT_FUNDS", "message": "Insufficient funds." } }
```

---

## 3. Error codes

| Code | Meaning | Suggested HTTP status (real API) |
|---|---|---|
| `VALIDATION_ERROR` | A field is missing or invalid (amount ≤ 0, more than 2 decimals, transfer to your own account, bad account number format, bad email). | 400 |
| `INVALID_CREDENTIALS` | Wrong user ID, email or password. Use one message for all cases. | 401 |
| `UNAUTHORIZED` | No valid token, the token expired, or the user no longer exists. | 401 |
| `ACCOUNT_NOT_FOUND` | The account (or the transfer recipient's account) does not exist. | 404 |
| `EMAIL_ALREADY_TAKEN` | Registration or profile update with an email that belongs to another user. | 409 |
| `INSUFFICIENT_FUNDS` | Withdraw or transfer amount is greater than the balance. | 422 |

When the real API arrives, HTTP errors must be translated into this envelope inside the services, so components keep working unchanged.

## 4. Models

### User

```ts
type Gender = 'MALE' | 'FEMALE' | 'NON_BINARY';

interface User {
  id: string;         // generated user ID, e.g. "ML1001"
  firstName: string;
  lastName: string;
  email: string;
  gender?: Gender;    // optional, set from the profile page
}
```

```json
{ "id": "ML1001", "firstName": "Molly", "lastName": "Lee", "email": "molly.lee@example.com", "gender": "FEMALE" }
```

| Field | Type | Required | Description |
|---|---|---|---|
| id | string | Yes | Unique user ID |
| firstName | string | Yes | User's first name |
| lastName | string | Yes | User's last name |
| email | string | Yes | User's email address, unique across users |
| gender | string | No | `MALE`, `FEMALE` or `NON_BINARY` |

### LoginRequest / RegisterRequest / AuthResponse

```ts
interface LoginRequest {
  identifier: string;   // user ID (e.g. "ML1001") OR email
  password: string;
}

interface RegisterRequest {
  firstName: string;
  lastName: string;
  email: string;
  password: string;     // no id: the server generates it
}

interface AuthResponse {   // returned by login only (register returns just the new User)
  user: User;
  token: string;
}
```

```json
{ "identifier": "molly.lee@example.com", "password": "1234" }
```

```json
{ "success": true, "data": { "user": { "id": "ML1001", "firstName": "Molly", "lastName": "Lee", "email": "molly.lee@example.com" }, "token": "mock-token-ML1001" } }
```

The token is simulated for frontend development. A production backend must provide a secure authentication token.

### UpdateProfileRequest

```ts
interface UpdateProfileRequest {
  firstName: string;
  lastName: string;
  email: string;
  gender?: Gender;
}
```

```json
{ "firstName": "Molly", "lastName": "Lee", "email": "molly.lee@example.com", "gender": "FEMALE" }
```

| Field | Type | Required | Description |
|---|---|---|---|
| firstName | string | Yes | User's first name |
| lastName | string | Yes | User's last name |
| email | string | Yes | Must be a valid email and unique across users |
| gender | string | No | `MALE`, `FEMALE` or `NON_BINARY` |

The user ID cannot be changed. The call returns the updated `User`.

### Account

```ts
type AccountType = 'CHECKING' | 'SAVINGS';

interface Account {
  id: string;
  userId: string;          // User.id
  accountNumber: string;   // exactly 10 digits
  balance: number;         // dollars, max 2 decimals
  currency: 'USD';
  type: AccountType;
}
```

```json
{ "id": "AC1001", "userId": "ML1001", "accountNumber": "1000001001", "balance": 2450.00, "currency": "USD", "type": "CHECKING" }
```

| Field | Type | Required | Description |
|---|---|---|---|
| id | string | Yes | Unique account ID |
| userId | string | Yes | ID of the account owner |
| accountNumber | string | Yes | Customer-facing account number, exactly 10 digits |
| balance | number | Yes | Current account balance |
| currency | string | Yes | Account currency (`USD`) |
| type | string | Yes | `CHECKING` or `SAVINGS` |

### Transaction

```ts
type TransactionType = 'DEPOSIT' | 'WITHDRAW' | 'TRANSFER_IN' | 'TRANSFER_OUT';

interface Transaction {
  id: string;
  accountId: string;                // the account this record belongs to
  type: TransactionType;
  amount: number;                   // always positive
  relatedAccountNumber?: string;    // the other party; only for TRANSFER_IN / TRANSFER_OUT
  description?: string;             // optional user message
  balanceAfter: number;             // balance of accountId right after this record
  createdAt: string;                // ISO 8601 UTC
}
```

`DEPOSIT` and `TRANSFER_IN` add to the balance. `WITHDRAW` and `TRANSFER_OUT` subtract from it.

```json
{ "id": "t4", "accountId": "AC1001", "type": "TRANSFER_OUT", "amount": 200, "relatedAccountNumber": "1000000002", "description": "rent share", "balanceAfter": 2250, "createdAt": "2026-10-03T16:45:00Z" }
```

| Field | Type | Required | Description |
|---|---|---|---|
| id | string | Yes | Unique transaction ID |
| accountId | string | Yes | Account this record belongs to |
| type | string | Yes | `DEPOSIT`, `WITHDRAW`, `TRANSFER_IN` or `TRANSFER_OUT` |
| amount | number | Yes | Always positive |
| relatedAccountNumber | string | No | The other party. Only for `TRANSFER_IN` / `TRANSFER_OUT` |
| description | string | No | Optional message from the user |
| balanceAfter | number | Yes | Balance of the account right after this record |
| createdAt | string | Yes | ISO 8601 UTC timestamp |

## 5. Operations

Service method names are the frontend contract. The REST paths are a **proposal** for the backend team.

| Service method | Proposed endpoint | Request | `data` on success | Possible error codes |
|---|---|---|---|---|
| login | `POST /auth/login` | `LoginRequest` | `AuthResponse` | `INVALID_CREDENTIALS`, `VALIDATION_ERROR` |
| register | `POST /auth/register` | `RegisterRequest` | `User` (the new user with its generated ID; no token, the user must log in next) | `EMAIL_ALREADY_TAKEN`, `VALIDATION_ERROR` |
| updateProfile | `PATCH /users/{userId}` | `UpdateProfileRequest` | `User` (the updated user) | `VALIDATION_ERROR`, `EMAIL_ALREADY_TAKEN`, `UNAUTHORIZED` |
| getAccountsByUserId | `GET /users/{userId}/accounts` | none | `Account[]` (all of the user's accounts) | `UNAUTHORIZED` |
| getAccountByUserId | `GET /users/{userId}/account` | none | `Account` (the user's `CHECKING` account) | `ACCOUNT_NOT_FOUND`, `UNAUTHORIZED` |
| getAccount | `GET /accounts/{accountId}` | none | `Account` | `ACCOUNT_NOT_FOUND`, `UNAUTHORIZED` |
| getTransactions | `GET /accounts/{accountId}/transactions` | none | `Transaction[]` (newest first) | `ACCOUNT_NOT_FOUND`, `UNAUTHORIZED` |
| getRecipients | `GET /accounts/{accountId}/recipients` | none | `Recipient[]` (never includes the caller's own account) | `ACCOUNT_NOT_FOUND`, `UNAUTHORIZED` |
| deposit | `POST /transactions/deposit` | `DepositRequest` | `Transaction` | `VALIDATION_ERROR`, `ACCOUNT_NOT_FOUND`, `UNAUTHORIZED` |
| withdraw | `POST /transactions/withdraw` | `WithdrawRequest` | `Transaction` | `VALIDATION_ERROR`, `ACCOUNT_NOT_FOUND`, `INSUFFICIENT_FUNDS`, `UNAUTHORIZED` |
| transfer | `POST /transactions/transfer` | `TransferRequest` | `Transaction` (the sender's `TRANSFER_OUT`) | `VALIDATION_ERROR`, `ACCOUNT_NOT_FOUND`, `INSUFFICIENT_FUNDS`, `UNAUTHORIZED` |

Money operations must be atomic: a transfer either updates both balances and writes both records, or changes nothing.

`createAccount(userId)` exists only in the mock `TransactionService`. A real backend creates the account itself when a user registers, so the frontend will not call it.

### Registration and login flow

1. A user with no credentials goes to **Register** (first name, last name, email, password, confirm password). There is **no username field**.
2. The server creates the user, generates the user ID (section 1) and creates a `CHECKING` account for them with balance 0. It returns the new `User`. Registering does **not** log the user in.
3. The app sends the user to **Login** and shows the generated user ID.
4. The user logs in with the user ID **or** the email, plus the password. On success the app receives `AuthResponse`, stores the user for the session, and goes to the dashboard.
5. Pages other than login and register require a logged-in user. Without one, the app redirects to Login.

In the mock, step 2's account is created the first time the new user opens the dashboard or the transactions page (`TransactionService.createAccount`).

### Profile flow

1. The profile page shows the logged-in user's current values in the form. The user ID is shown read-only.
2. The user edits first name, last name, email (with a confirm-email field) and optionally gender, then saves.
3. On success, the app updates the stored user, so the navbar, welcome messages and every other page show the new values immediately.

## 6. Validation rules

| Field | Rule |
|---|---|
| `amount` | Required, greater than 0, at most 2 decimals. |
| `toAccountNumber` | Required, exactly 10 digits, must exist, must not be the sender's own account. |
| `description` | Optional free text. |
| `email` | Must be a valid email format and unique across users (`EMAIL_ALREADY_TAKEN`). |
| `firstName`, `lastName` | Required, cannot be empty. |
| Profile `email` | Must match the Confirm Email field (checked in the form only; the confirm value is never sent). |
| Registration `password` | Must meet the app's minimum length and match the confirm-password field (checked in the form). |
| Withdraw / transfer | `amount` must not exceed the account balance (`INSUFFICIENT_FUNDS`). |

The frontend validates these before sending (a form never submits an invalid value), and the service validates again, as the real backend will.

## 8. Mock-only behaviour (goes away with the real API)

- `TransactionService` loads the three files in `public/mock/` once and keeps the data in memory. After each deposit, withdraw, transfer or account creation, it saves the whole dataset to the browser's `localStorage` (key `bank-of-airlines-mock-db-v1`), so changes survive a page refresh.
- The saved copy wins over the JSON files. After you edit anything in `public/mock/`, clear Local Storage for the site (DevTools → Application → Local Storage), or bump the key's version.
- A fake delay (about 600 ms) simulates network time on transactions, money operations and account lists, so loading states are visible.
- The signed-in user is stored in `localStorage` under the key `currentUser`, so a refresh keeps you signed in. `AuthService.login` stores it and tells `CurrentUserService`, and `AuthService.logout` clears both. Profile edits update the same stored user.
- Users registered in the mock live in memory only and are lost when the dev server restarts.

## 9. TypeScript contract layer

The TypeScript interfaces used by the frontend are stored in `src/app/core/models/`:

- `user.model.ts` (`User`, `Gender`, `UpdateProfileRequest`, login and register types)
- `account.model.ts` (`Account`, `AccountType`)
- `transaction.model.ts` (`Transaction`, `TransactionType`, deposit / withdraw / transfer requests)
- `reciepient.model.ts` (`Recipient`; the file name has a typo, rename it later)
- `api-response.model.ts` (`ApiResponse`, `ApiError`, `ApiErrorCode`)

These interfaces define the data structures used throughout the Angular application.

## 10. Service layer

Components talk to services, never directly to mock data.

| Service | File | Responsibility |
|---|---|---|
| `AuthService` | `core/services/auth.service.ts` | `login`, `register`, `updateProfile`, `getCurrentUser`, `logout` |
| `CurrentUserService` | `core/services/current.user.services.ts` | Holds the logged-in user, shared by every page (navbar, welcome cards, transactions) |
| `TransactionService` | `core/services/transaction.service.ts` | Accounts, transactions, recipients, `deposit`, `withdraw`, `transfer`, `createAccount` |

This lets the mock data source be replaced by backend API calls later without touching components.

---

## 11. Route protection

Authenticated pages are protected by the authentication guard, and render inside the shared layout (navbar and sidebar).

Protected routes: `/dashboard`, `/transactions`, `/profile`, `/help`.

Public routes: `/login`, `/register`.

Unauthenticated users who open a protected route are redirected to `/login`.

## 12. Future backend integration

During the mock phase:

```
Component → Service → Mock JSON data
```

When the backend exists:

```
Component → Service → Backend API → Database
```

The backend must keep the field names, data types and structures in this document. Changes to the contract must be agreed between the frontend and backend teams before implementation. The goal is to move from mock data to real API data with minimal changes to the component layer.
