# Bank of CLI — API Contract

This document defines the JSON structures exchanged between the frontend and the backend.
The frontend's mock services (`src/services/`) return data that follows this contract exactly,
so the real backend can replace them without UI changes.

TypeScript definitions for every shape below live in `src/models/`.

---

## 1. Conventions

| Topic | Rule |
|---|---|
| Format | All requests and responses are JSON (`Content-Type: application/json`). |
| Field names | camelCase (e.g. `accountNumber`, `amountCents`). |
| Money | Always an **integer number of cents**. `10050` = $100.50. Never decimals. |
| Account numbers | 10-digit **strings**, e.g. `"1000004821"`. |
| Transaction IDs | **Strings**, e.g. `"TXN-20261007-000123"` (see §5). |
| Timestamps | ISO 8601 UTC strings, e.g. `"2026-10-07T14:30:00Z"`. |
| Authentication | Authenticated endpoints require `Authorization: Bearer <token>`. |
| Errors | Every error response uses the `ApiError` shape (see §4). |

---

## 2. Data Models

### User
```json
{
  "id": "u_1",
  "firstName": "Alice",
  "lastName": "Smith",
  "username": "asmith1234",
  "email": "alice@bank.com"
}
```
- `username` is generated by the server (see §5). Users cannot choose it.
- Passwords are **never** included in any response.

### Account
```json
{
  "accountNumber": "1000001234",
  "balanceCents": 250000,
  "userId": "u_1"
}
```
- Each user currently has exactly one account.

### Transaction
```json
{
  "id": "TXN-20261007-000123",
  "type": "transfer",
  "amountCents": 5000,
  "fromAccountNumber": "1000001234",
  "toAccountNumber": "1000005678",
  "timestamp": "2026-10-07T14:30:00Z"
}
```
| `type` | `fromAccountNumber` | `toAccountNumber` |
|---|---|---|
| `deposit` | `null` | user's account |
| `withdrawal` | user's account | `null` |
| `transfer` | sender's account | recipient's account |

- `amountCents` is always positive. Direction is determined by the account fields.
- For transfers, the UI shows "incoming" or "outgoing" by comparing the account numbers to the logged-in user's account.

## 3. Endpoints

### Summary

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| POST | `/auth/register` | No | `RegisterRequest` | `201` `AuthResponse` |
| POST | `/auth/login` | No | `LoginRequest` | `200` `AuthResponse` |
| GET | `/accounts/me` | Yes | — | `200` `Account` |
| GET | `/transactions` | Yes | query params | `200` `PaginatedTransactions` |
| POST | `/transactions/deposit` | Yes | `DepositRequest` | `201` `TransactionResponse` |
| POST | `/transactions/withdraw` | Yes | `WithdrawRequest` | `201` `TransactionResponse` |
| POST | `/transactions/transfer` | Yes | `TransferRequest` | `201` `TransactionResponse` |

Logout has no endpoint. The frontend discards the token.

---

### POST /auth/register

Creates a user and an account with a `0` balance.

**Request** — `RegisterRequest`
```json
{
  "firstName": "John",
  "lastName": "Doe",
  "email": "john@example.com",
  "password": "secret123"
}
```

**201 Created** — `AuthResponse`
```json
{
  "user": {
    "id": "u_1728311400000",
    "firstName": "John",
    "lastName": "Doe",
    "username": "jdoe4821",
    "email": "john@example.com"
  },
  "account": {
    "accountNumber": "1000004821",
    "balanceCents": 0,
    "userId": "u_1728311400000"
  },
  "token": "mock-token-u_1728311400000"
}
```

**Errors**
| Status | Code | When | `field` |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | Invalid first name, last name, or email | `firstName` / `lastName` / `email` |
| 400 | `WEAK_PASSWORD` | Password fails the rules in §5 | `password` |
| 409 | `EMAIL_TAKEN` | Email already registered | `email` |

```json
{ "code": "EMAIL_TAKEN", "message": "An account with this email already exists.", "field": "email" }
```

---

### POST /auth/login

Accepts **either** a username or an email as the identifier.

**Request** — `LoginRequest`
```json
{ "identifier": "asmith1234", "password": "password1" }
```
or
```json
{ "identifier": "alice@bank.com", "password": "password1" }
```

**200 OK** — `AuthResponse` (same shape as register).

**Errors**
| Status | Code | When |
|---|---|---|
| 401 | `INVALID_CREDENTIALS` | Unknown identifier or wrong password |

```json
{ "code": "INVALID_CREDENTIALS", "message": "Invalid username/email or password." }
```
The same message is returned whether the identifier or the password is wrong, so attackers cannot discover which usernames exist.

### GET /accounts/me

Returns the logged-in user's account.

**200 OK** — `Account`
```json
{ "accountNumber": "1000001234", "balanceCents": 250000, "userId": "u_1" }
```

**Errors**
| Status | Code | When |
|---|---|---|
| 401 | `UNAUTHORIZED` | Missing or invalid token |

### GET /transactions

Returns a page of transactions involving the logged-in user's account (as sender or recipient), **newest first**.

Mock implementation: `getTransactionsFromId(accountNumber, type, page)` in `src/services/transactionService.ts`.

**Query parameters**
| Param | Type | Default | Description |
|---|---|---|---|
| `type` | `TransactionType` \| `"all"` | `"all"` | Optional filter by transaction type |
| `page` | number | `0` | Zero-based page index |

Page size is fixed at **3** transactions.

Example: `GET /transactions?type=transfer&page=1`

**200 OK** — `PaginatedTransactions`
```json
{
  "transactions": [
    {
      "id": "TXN-20261007-000021",
      "type": "withdrawal",
      "amountCents": 2150,
      "fromAccountNumber": "1000001234",
      "toAccountNumber": null,
      "timestamp": "2026-10-07T12:05:00Z"
    },
    {
      "id": "TXN-20261006-000020",
      "type": "transfer",
      "amountCents": 30000,
      "fromAccountNumber": "1000005678",
      "toAccountNumber": "1000001234",
      "timestamp": "2026-10-06T09:58:00Z"
    },
    {
      "id": "TXN-20261004-000018",
      "type": "withdrawal",
      "amountCents": 8999,
      "fromAccountNumber": "1000001234",
      "toAccountNumber": null,
      "timestamp": "2026-10-04T15:42:00Z"
    }
  ],
  "totalPages": 4
}
```
- `totalPages` is `0` and `transactions` is `[]` when the account has no transactions.
- Requesting a page past the end returns an empty `transactions` array with the same `totalPages`.

**Errors**
| Status | Code | When |
|---|---|---|
| 401 | `UNAUTHORIZED` | Missing or invalid token |

### POST /transactions/deposit

**Request** — `DepositRequest`
```json
{ "accountNumber": "1000001234", "amountCents": 10000 }
```

**201 Created** — `TransactionResponse`
```json
{
  "transaction": {
    "id": "TXN-20261007-000124",
    "type": "deposit",
    "amountCents": 10000,
    "fromAccountNumber": null,
    "toAccountNumber": "1000001234",
    "timestamp": "2026-10-07T15:00:00Z"
  },
  "newBalanceCents": 260000
}
```

**Errors**
| Status | Code | When |
|---|---|---|
| 400 | `INVALID_AMOUNT` | Amount is not a positive integer within limits |
| 401 | `UNAUTHORIZED` | Missing token, or the account does not belong to the user |

### POST /transactions/withdraw

**Request** — `WithdrawRequest`
```json
{ "accountNumber": "1000001234", "amountCents": 2500 }
```

**201 Created** — `TransactionResponse`
```json
{
  "transaction": {
    "id": "TXN-20261007-000125",
    "type": "withdrawal",
    "amountCents": 2500,
    "fromAccountNumber": "1000001234",
    "toAccountNumber": null,
    "timestamp": "2026-10-07T15:10:00Z"
  },
  "newBalanceCents": 257500
}
```

**Errors**
| Status | Code | When |
|---|---|---|
| 400 | `INVALID_AMOUNT` | Amount is not a positive integer within limits |
| 422 | `INSUFFICIENT_FUNDS` | Amount exceeds the balance |
| 401 | `UNAUTHORIZED` | Missing token, or the account does not belong to the user |

---

### POST /transactions/transfer

**Request** — `TransferRequest`
```json
{
  "fromAccountNumber": "1000001234",
  "toAccountNumber": "1000005678",
  "amountCents": 5000
}
```

**201 Created** — `TransactionResponse`
```json
{
  "transaction": {
    "id": "TXN-20261007-000126",
    "type": "transfer",
    "amountCents": 5000,
    "fromAccountNumber": "1000001234",
    "toAccountNumber": "1000005678",
    "timestamp": "2026-10-07T15:20:00Z"
  },
  "newBalanceCents": 252500
}
```
`newBalanceCents` is the **sender's** new balance.

**Errors**
| Status | Code | When | `field` |
|---|---|---|---|
| 400 | `INVALID_AMOUNT` | Amount is not a positive integer within limits | `amountCents` |
| 400 | `SAME_ACCOUNT_TRANSFER` | `toAccountNumber` equals `fromAccountNumber` | `toAccountNumber` |
| 404 | `ACCOUNT_NOT_FOUND` | Recipient account does not exist | `toAccountNumber` |
| 422 | `INSUFFICIENT_FUNDS` | Amount exceeds the sender's balance | `amountCents` |
| 401 | `UNAUTHORIZED` | Missing token, or `fromAccountNumber` does not belong to the user | — |

## 4. Errors

Every error response has this shape:

```json
{
  "code": "INSUFFICIENT_FUNDS",
  "message": "Insufficient funds for this withdrawal.",
  "field": "amountCents"
}
```

- `code` — machine-readable; the UI uses it for logic.
- `message` — user-friendly; the UI shows it in toasts or under inputs.
- `field` — optional; names the request field that caused the error, so the UI can show the message under that input.

| Code | HTTP status | Meaning |
|---|---|---|
| `INVALID_CREDENTIALS` | 401 | Wrong identifier or password |
| `UNAUTHORIZED` | 401 | Missing/invalid token, or acting on another user's account |
| `EMAIL_TAKEN` | 409 | Email already registered |
| `ACCOUNT_NOT_FOUND` | 404 | Account number does not exist |
| `INSUFFICIENT_FUNDS` | 422 | Balance too low |
| `INVALID_AMOUNT` | 400 | Zero, negative, non-integer, or over the limit |
| `SAME_ACCOUNT_TRANSFER` | 400 | Transfer to the sender's own account |
| `WEAK_PASSWORD` | 400 | Password fails the rules |
| `VALIDATION_ERROR` | 400 | Any other invalid input |

## 5. Business Rules

These rules are enforced by both the frontend (for immediate feedback) and the backend (as the source of truth).

### Registration
- **First and last name:** required; must contain at least one letter.
- **Email:** required; valid format (`name@domain.tld`); unique (case-insensitive); stored lowercase.
- **Password:** at least 8 characters, including at least one number.

### Generated values
- **Username:** first initial + last name, lowercase, letters only, base capped at 12 characters, followed by 4 random digits (1000–9999). Regenerated if already taken.
  Examples: John Doe → `jdoe4821`; Seán O'Brien-Smith → `sobriensmith1234`.
- **Account number:** 10 digits, between `1000000000` and `9999999999`, unique.
- **Transaction ID:** `TXN-YYYYMMDD-NNNNNN`, where `YYYYMMDD` is the UTC date of the transaction and `NNNNNN` is a zero-padded sequence number that increases across all transactions.

### Money
- All amounts are positive integers in cents.
- Maximum per transaction: `10000000000` cents ($100,000,000).
- Withdrawals and transfers cannot exceed the current balance.

### Authorization
- Users may only deposit to, withdraw from, or transfer from **their own** account.
- Transfers may go to any existing account other than the sender's.

## 6. Mock Implementation Notes

- Mock services simulate network latency (~800 ms) and return data matching this contract.
- Mock data lives in `src/mocks/` and is loaded into a shared in-memory store (`src/mocks/db.ts`).
- **Data resets on page refresh.** Newly registered users and new transactions are not persisted.
- Mock tokens have the form `mock-token-<userId>`. The real backend should issue a signed token (e.g. JWT).
- The frontend stores the session in `sessionStorage` under `bankofcli-auth`.

- Each account's `balanceCents` equals the sum of its transaction history in `transactions.json` (deposits and incoming transfers minus withdrawals and outgoing transfers).

## 7. Notes for the Backend Team

- The Part 1 schema used `NUMERIC(12,2)` for money. Store cents as `BIGINT` instead, or convert at the API boundary.
- The Part 1 schema used snake_case columns. Convert to camelCase in JSON responses.
- The Part 1 PIN is replaced by a hashed password. Never return password hashes.
- A `users` table is needed (Part 1 had accounts only), with `accounts.user_id` referencing it.
- Start the account number sequence at `1000000000`.
